# 로컬 개발 환경 (dev)

이 가이드는 미니앱을 **토스 앱 없이** 개발하는 station 2(dev)의 셋업을 다룹니다. 핵심 도구는 세 가지이고, 각각 서로 다른 목적을 가집니다 — 하나로 다 되는 게 아니라, 개발 루프의 단계마다 더 실제에 가까운 환경으로 올라가는 **사다리**입니다.

:::info 자동화는 `/ait` 스킬로
아래 셋업은 [agent-plugin](https://github.com/apps-in-toss-community/agent-plugin)의 `/ait` 스킬로 에이전트 안에서 끝낼 수 있습니다 — `/ait inject-devtools`(브라우저 mock), `/ait inject-polyfill`(표준 Web API), `/ait setup-phone-preview`(실기기 미리보기). 이 가이드는 그 스킬들이 안에서 무슨 파일을 어떻게 패치하는지, 왜 그렇게 하는지를 설명합니다.
:::

## 세 가지 셋업 한눈에

| 셋업 | `/ait` 스킬 | 무엇을 | 어느 환경 |
|---|---|---|---|
| devtools mock | `/ait inject-devtools` | 빌드 도구에 unplugin 주입 → 브라우저에서 SDK를 mock으로 실행 + DevTools 패널 | 환경 1 (로컬 브라우저) |
| polyfill | `/ait inject-polyfill` | 표준 Web API 호출을 런타임에 SDK로 라우팅하는 shim 설치 | 환경 1 (작성 방식 옵션) |
| 실기기 미리보기 | `/ait setup-phone-preview` | quick-tunnel + launcher PWA 배선 → 실폰 Safari/WebKit에서 dev 앱 미리보기 | 환경 2 (실기기 PWA) |

세 셋업은 독립적입니다. devtools mock만으로도 개발이 되고, polyfill은 작성 스타일을 바꾸는 선택지이며, 실기기 미리보기는 브라우저가 구조적으로 못 하는 것(실제 WebKit 엔진)을 확인할 때 올라가는 한 겹 위입니다.

## fidelity 사다리 — 왜 한 환경으로 안 끝나나

미니앱 개발 환경은 단일 환경이 아니라 **fidelity(실제에 얼마나 가까운가) 사다리** 위의 여러 겹입니다. 안쪽 겹이 구조적으로 못 하는 것을 바깥 겹이 메웁니다 — 그래서 "더 충실한 mock"을 끝없이 좇는 대신, 각 겹에서 그 겹이 잘하는 것에 집중하고 필요할 때만 위로 올라갑니다.

```
환경 1  로컬 브라우저 (devtools mock + 패널)
        → 상태/계약 정합 + 시각 레이아웃. 즉시. 엔진 fidelity는 구조적으로 불가.
환경 2  실기기 PWA (launcher + quick-tunnel)
        → 실제 WebKit 엔진 + 실 터치/뷰포트. 폰 1회 설치. 토스 검수 불필요.
```

- **환경 1(브라우저)**: 가장 빠른 루프. SDK가 mock으로 동작하므로 토스 앱·실기기 없이 상태 전이와 계약(어떤 인자로 무엇이 호출되는지)을 검증하고, 레이아웃을 눈으로 확인합니다. 다만 실제 토스 WebView 엔진이 아니므로 엔진 수준 차이(특정 CSS·뷰포트·터치 거동)는 여기서 못 잡습니다 — 그건 구조적 한계라 환경 2에 위임합니다.
- **환경 2(실기기 PWA)**: 실폰 Safari/WebKit에서 dev 앱을 띄워 실제 엔진·터치·safe-area를 확인합니다. 토스 앱 검수가 필요 없어 환경 1과 출시 사이의 빈 구간을 메웁니다.

더 위 겹(실제 토스 앱 WebView에서의 디버깅)은 출시·운영 단계의 디버그 relay가 담당합니다 — [번들 디버그 relay](/guides/debug-relay) 참고.

## 셋업 1 — 브라우저 mock (`/ait inject-devtools`)

`@ait-co/devtools`는 `@apps-in-toss/web-framework` SDK를 브라우저에서 mock으로 실행하는 unplugin입니다. 빈 프로젝트는 `/ait new` 스캐폴드에 이미 들어 있지만, **기존(brownfield) 프로젝트**에 뒤늦게 붙일 때 `/ait inject-devtools`를 씁니다.

이 스킬이 하는 일:

1. 빌드 도구 감지 — Vite / Next.js / Rspack / Webpack 중 무엇인지.
2. 패키지 매니저에 맞게 `@ait-co/devtools`를 dev dependency로 설치.
3. config 파일(`vite.config.ts` 등)에 unplugin을 **멱등하게** 추가 — 이미 있으면 중복 추가하지 않습니다.

붙이고 나면 `pnpm dev`로 브라우저를 띄웠을 때 SDK 호출이 mock으로 응답하고, DevTools 패널에서 호출 로그(`sdkCallLog`)와 no-op API 가시화를 볼 수 있습니다. mock은 토스 앱 WebView 동작에 맞춰 정렬돼 있어, 상태/계약 수준에서는 실제와 같은 코드 경로를 탑니다.

## 셋업 2 — 표준 Web API (`/ait inject-polyfill`)

`@ait-co/polyfill`은 미니앱을 **표준 Web API**로 작성할 수 있게 해주는 shim입니다. 예를 들어 클립보드를 SDK 전용 함수 대신 표준 `navigator.clipboard` 형태로 호출하면, shim이 런타임에 그 호출을 SDK로 라우팅합니다.

`/ait inject-polyfill`이 하는 일:

1. `@ait-co/polyfill` 설치.
2. 진입점(`--entry <path>`로 지정, 기본은 자동 탐지)에 auto-import 한 줄을 배선.
3. 표준 Web API로 작성하는 패턴 안내.

이 셋업은 **선택**입니다. polyfill 없이 SDK 함수를 직접 써도 됩니다. polyfill의 가치는 SDK 버전 중립성입니다 — shim이 SDK를 정적 import하지 않고 런타임에 함수를 probe하므로, 함수명이 같은 한 SDK 메이저 버전이 올라가도 코드를 거의 안 건드립니다.

## 셋업 3 — 실기기 미리보기 (`/ait setup-phone-preview`)

환경 1(브라우저)이 구조적으로 못 하는 실제 WebKit 엔진을 확인하려면 환경 2로 올라갑니다. `/ait setup-phone-preview`는 dev 서버를 실폰에서 띄우는 배선을 한 번에 합니다.

이 스킬이 패치하는 것 (전부 멱등):

1. `vite.config.ts` — devtools unplugin에 quick-tunnel 옵션 추가.
2. `pnpm-workspace.yaml` — `cloudflared`를 `onlyBuiltDependencies`에 추가.
3. `package.json` — `dev:phone` 스크립트 추가.
4. `pnpm install` 실행 — 첫 실행 전에 `cloudflared` 바이너리를 캐시.

배선 후 `pnpm dev:phone`을 띄우면 quick-tunnel로 로컬 dev 서버가 공개 URL로 노출되고, launcher PWA(`devtools.aitc.dev/launcher/`)를 통해 실폰 Safari에서 설치형 PWA로 미리볼 수 있습니다. 토스 앱 WebView가 아니라 실기기 WebKit 엔진이므로, 엔진·터치·뷰포트·safe-area를 실제로 확인할 수 있습니다.

:::caution 터널은 공개 URL입니다
quick-tunnel은 인증 없는 공개 URL을 만듭니다. dev 미리보기 용도로만 쓰고, 민감한 데이터를 그 위에 올리지 마세요. 디버그 relay(환경 3·4)는 별도의 시크릿 기반 TOTP 인증으로 닫힙니다 — [relay 인증 TOTP](/guides/relay-auth-totp) 참고.
:::

## 어느 셋업을 언제

- **막 시작했다 / 빈 프로젝트** — `/ait new` 스캐폴드에 devtools가 이미 들어 있습니다. 별도 주입 불필요.
- **기존 프로젝트에 mock을 붙이고 싶다** — `/ait inject-devtools`.
- **표준 Web API로 작성하고 싶다** — `/ait inject-polyfill` (선택).
- **브라우저로는 못 잡는 엔진·터치·레이아웃을 실폰에서 확인하고 싶다** — `/ait setup-phone-preview`.
- **실제 토스 앱 WebView에서 디버깅하고 싶다** — 환경 1·2를 넘어서는 단계로, 출시 번들을 실기기에 cold-load하는 [디버그 relay](/guides/debug-relay)입니다.
