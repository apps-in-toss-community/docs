# 미니앱 번들 빌드·등록·배포 (ship)

이 가이드는 미니앱 하나를 **번들 빌드 → 콘솔 등록 → 업로드 → 출시 검수 제출**까지 끌고 가는 station 5(register+ship)의 전 과정을 다룹니다. 명령은 두 개의 서로 다른 CLI에 나뉘어 있고, 검수는 두 개의 독립된 상태머신으로 진행됩니다. 이 두 가지를 흐리면 "분명히 등록은 됐는데 왜 앱이 안 열리지?" 같은 막힘에 빠지기 쉬우므로, 가이드 전체에서 어느 CLI·어느 상태머신인지를 매번 명시합니다.

:::info 자동화는 `/ait` 스킬로
아래 모든 단계는 [agent-plugin](https://github.com/apps-in-toss-community/agent-plugin)의 `/ait` 스킬로 에이전트 안에서 끝낼 수 있습니다 — `/ait setup-bundle` → `/ait register` → `/ait deploy-key` → `/ait deploy`. 이 가이드는 그 스킬들이 안에서 실제로 무슨 명령을 부르는지, 왜 그렇게 부르는지를 설명합니다.
:::

## 먼저: 두 CLI를 구분하기

ship 흐름에는 이름이 비슷한 두 CLI가 등장합니다. 둘은 **다른 도구**이고 역할이 겹치지 않습니다.

| CLI | 패키지 | 역할 | 이 가이드에서 쓰는 명령 |
|---|---|---|---|
| `ait` | `@apps-in-toss/cli` (번들러) | 미니앱을 `.ait` 번들로 빌드하고, 번들을 배포 큐에 업로드 | `ait build`, `ait deploy --profile <name>` |
| `aitcc` | `@ait-co/console-cli` (커뮤니티 콘솔 자동화) | 앱인토스 콘솔을 자동화 — 앱 등록, Deploy Key 발급, 출시 검수 제출·상태 조회 | `aitcc app register`, `aitcc keys create`, `aitcc app deploy`, `aitcc app status` |

핵심 분담:

- **번들을 만들고 올리는 건 `ait`** (번들러 바이너리). `ait build`가 `<appName>.ait`를 만들고, `ait deploy`가 그 번들을 콘솔의 배포 큐에 PUT합니다.
- **콘솔을 다루는 건 `aitcc`** (커뮤니티 콘솔 CLI). 앱 메타데이터 등록, Deploy Key 발급, 출시 검수 제출, 상태 조회가 전부 `aitcc`입니다.

한 가지 헷갈리는 지점: 번들 업로드는 `ait deploy`로도, `aitcc app deploy`로도 할 수 있습니다. 둘 다 같은 콘솔 배포 엔드포인트를 칩니다. 보통 **업로드는 Deploy Key를 쓰는 `ait deploy --profile`**로 하고(로컬·CI 인증이 깔끔), **출시 검수 제출은 콘솔 세션을 쓰는 `aitcc app deploy --request-review`**로 합니다 — 검수 제출은 비가역이라 의식적으로 분리합니다. 아래에서 단계별로 짚습니다.

## 전체 흐름 한눈에

```
ait build                      → <appName>.ait 번들 생성            (번들러, 로컬)
aitcc app register             → 콘솔에 앱 메타데이터 등록·검수 제출 (콘솔)
aitcc keys create              → Deploy Key 발급                    (콘솔)
ait deploy --profile <name>    → 번들을 배포 큐에 업로드            (번들러)
aitcc app deploy --request-review --release-notes "<text>"
                               → 업로드된 번들을 출시 검수에 제출   (콘솔)
aitcc app deploy --release --confirm
                               → 검수 통과한 번들을 실제 출시        (콘솔, 2차 실행)
```

번들 빌드 환경 추가는 `/ait setup-bundle`, 등록은 `/ait register`, Deploy Key는 `/ait deploy-key`, 업로드는 `/ait deploy`가 각각 담당합니다.

## 1단계 — 번들 빌드 (`ait build`)

먼저 프로젝트에 번들 빌드 환경이 있어야 합니다. `/ait setup-bundle`이 `@apps-in-toss/cli`를 devDependency로 추가하고 `granite.config.ts`를 생성하며 `package.json`에 `bundle:ait` 스크립트(내부적으로 `ait build`)를 깔아줍니다.

`granite.config.ts`의 최소 형태:

```ts
import { defineConfig } from '@apps-in-toss/web-framework/config';

export default defineConfig({
  appName: 'my-mini-app',
  brand: {
    displayName: '내 미니앱',
    primaryColor: '#3182F6',
    icon: 'https://example.com/icon.png', // SDK 2.x에서 필수 — 호스팅된 https URL이어야 함
  },
  web: {
    host: 'localhost',
    port: 5173,
    commands: { dev: 'vite', build: 'vite build' },
  },
  permissions: [],
  outdir: 'dist',
});
```

번들을 만듭니다.

```bash
pnpm bundle:ait        # 내부적으로 ait build 실행 → <appName>.ait 생성
```

`brand.icon`은 SDK 2.x에서 필수 필드입니다 — 비우거나 로컬 파일 경로를 쓰면 `[Apps In Toss Plugin] 플러그인 옵션이 올바르지 않습니다.` 오류로 빌드가 실패합니다. 호스팅된 `https://` URL을 넣으세요.

`.ait` 번들 안에는 `deploymentId`가 임베드돼 있습니다 — 나중에 `ait deploy`가 이 값을 자동으로 추출하므로, 업로드 시 따로 지정할 필요가 없습니다.

## 2단계 — 콘솔에 앱 등록 (`aitcc app register`)

번들 빌드는 로컬 작업이라 인증이 필요 없지만, **콘솔 등록부터는 로그인된 `aitcc` 세션**이 필요합니다. `aitcc login`이 시스템 Chrome 창을 열어 콘솔(`apps-in-toss.toss.im`)에 로그인하게 하고, 세션 쿠키를 로컬에 저장합니다. (대화형 로그인이라 에이전트는 직접 호출하지 않고 사용자가 한 번 실행합니다.)

등록은 `aitcc.yaml` 매니페스트 한 파일로 콘솔의 앱 등록 마법사를 자동화합니다. `/ait register`가 이 매니페스트를 비대화형으로 생성합니다(콘솔 UI의 `aitcc app init`은 TTY 전용이라 에이전트가 못 돌립니다).

매니페스트 필수 필드의 일부 제약:

| 필드 | 제약 |
|---|---|
| `titleKo` | 한글·영문·숫자·공백 + `: · ?`만. 공백 제외 10 코드포인트 이하 |
| `titleEn` | `[A-Za-z0-9 :·?]`만. 공백 제외 15 코드포인트 이하. 각 단어 Title-Case(예: `Aitc Sdk Example` — `AITC`·`SDK` 같은 전부 대문자 토큰은 거부) |
| `appName` | `^[a-z][a-z0-9-]*$` (소문자 시작 kebab-case), 앱인토스 전체에서 unique |
| `categoryIds` | 정수 1개 이상. `aitcc app categories --selectable --json`으로 라이브 조회 |
| `logo` / `horizontalThumbnail` / `verticalScreenshots` | 규격 PNG (600×600 / 1932×828 / 각 636×1048, 세로 3장 이상) |

이미지 자산은 `./assets/`에 직접 배치합니다. 규격 PNG 생성은 디자인 station(`/ait design`)이 맡습니다.

제출 전에 항상 `--dry-run`으로 매니페스트와 이미지 규격을 먼저 검증하세요. dry-run은 약관 동의가 필요 없습니다.

```bash
aitcc app register --config ./aitcc.yaml --dry-run --json
```

실제 제출은 콘솔의 필수 약관 동의를 수반하므로 `--accept-terms`가 필요합니다.

```bash
aitcc app register --config ./aitcc.yaml --accept-terms --json
```

:::caution `--accept-terms`는 명시적 동의가 필요합니다
`--accept-terms`는 앱을 리뷰에 제출하고 콘솔의 필수 법적 약관에 동의하는 것을 의미합니다. CLI는 이 플래그가 없으면 제출을 거부하고 `exit 2`(`terms-not-accepted`)로 멈춥니다. 무엇에 동의하는지 확인한 뒤에만 붙이세요 — 에이전트가 임의로 붙여서는 안 됩니다.
:::

등록이 성공하면 서버가 돌려준 `miniAppId`가 `aitcc.yaml`에 자동 기록됩니다. 이후 `aitcc app deploy`·`aitcc app status` 같은 명령이 `--app` 인자 없이도 같은 앱을 가리킵니다.

## 두 검수는 별개의 상태머신입니다

이 가이드에서 가장 중요한 부분입니다. 미니앱 출시에는 **서로 독립적으로 진행되는 두 개의 검수**가 있습니다.

| | 앱 등록 검수 | 번들 출시 검수 |
|---|---|---|
| 대상 | 앱 메타데이터(제목·아이콘·스크린샷·카테고리) | 개별 번들(`deploymentId` 단위) |
| 상태 필드 | `approvalType` (앱 단위) | `reviewStatus` (번들 단위) |
| 트리거 | `aitcc app register` | `aitcc app deploy --request-review` |
| 상태 전이 | `REVIEW → APPROVED` / `REJECTED` | `CREATED → REVIEWING → APPROVED → RELEASED` |

두 검수는 한쪽이 통과해도 다른 쪽에 영향을 주지 않습니다. 그래서 **앱 등록은 `approved`인데도 앱이 사용자에게 안 보이는** 상황이 정상적으로 발생합니다 — 업로드된 번들이 아직 출시 검수를 통과하지 못했기 때문입니다.

### 앱 등록 검수 (`approvalType`)

```
create (aitcc app register, miniAppId 없음)
  → REVIEW ──(운영팀 통과)──→ APPROVED
         └──(운영팀 반려)──→ REJECTED (rejectedMessage 채워짐)

APPROVED ──(update)──→ REVIEW   (current 유지, 새 변경은 draft로)
REJECTED ──(update)──→ REVIEW   (draft 덮어씀)
REVIEW   ──(update)──→ ❌ errorCode 4046 (잠금)
```

이미 등록된 앱은 같은 `aitcc app register`에 `miniApp.miniAppId`가 들어간 update mode로 변경합니다 — 별도의 update 엔드포인트는 없습니다.

### 번들 출시 검수 (`reviewStatus`)

```
upload (ait deploy / aitcc app deploy)
  → CREATED ──(--request-review)──→ REVIEWING
          REVIEWING ──(운영팀 통과)──→ APPROVED ──(--release --confirm)──→ RELEASED
          REVIEWING ──(운영팀 반려)──→ REJECTED ──(재제출)──→ REVIEWING
```

업로드만 하면 번들은 `CREATED`에 머뭅니다(출시 검수 미제출). `--request-review`로 검수 큐에 넣고, 운영팀이 `APPROVED`로 통과시킨 뒤, `--release --confirm`으로 실제 출시합니다.

### 둘의 연결고리: `serviceStatus`

앱이 사용자에게 실제로 열렸는지는 `serviceStatus`(앱 단위)가 결정합니다.

- 앱 등록이 `APPROVED`여도, **첫 번째 `RELEASED` 번들이 나오기 전까지 `serviceStatus`는 `PREPARE`**입니다.
- 첫 `RELEASED` 번들이 생기면 `serviceStatus`가 `OPENED`로 전환되고, 그때부터 앱이 사용자에게 노출됩니다.

정리하면, 출시까지의 완전한 경로는 이렇습니다.

```
앱 등록 APPROVED  +  번들 CREATED → REVIEWING → APPROVED → RELEASED
                                                              ↓
                                              serviceStatus: PREPARE → OPENED
```

## 3단계 — Deploy Key 발급 (`aitcc keys create`)

번들 업로드(`ait deploy`)는 콘솔 세션이 아니라 **Deploy Key**로 인증합니다 — 워크스페이스 단위의 배포 자격증명입니다. 콘솔 UI는 이를 "API 키"라 부르지만, 발급은 `aitcc keys create`로 합니다.

`/ait deploy-key`가 발급과 저장을 한 번에 처리합니다.

```bash
aitcc keys create --name <label> --json
```

`aitcc keys create`는 기본적으로 발급된 키를 `~/.ait/credentials`(JSON, mode `0600`)에 **`--name`과 같은 이름의 프로파일로 자동 저장**합니다 — 이렇게 하면 이후 `ait deploy --profile <name>`이 키 값을 명령행에 노출하지 않고 바로 인증합니다. 프로파일 이름을 따로 두고 싶으면 `--save-profile <profile-name>`으로 자동 저장 이름을 덮어쓰고, 저장 자체를 끄려면(stdout으로만 받아 다른 곳에 보관) `--no-save-profile`을 씁니다.

:::caution Deploy Key는 한 번만 노출됩니다
발급된 Deploy Key 값은 발급 시점에 한 번만 노출됩니다(GitHub PAT과 같은 패턴). `--save-profile`로 즉시 안전하게 저장하고, 키 값을 로그·채팅·명령행에 다시 출력하지 마세요. CI에서 쓰려면 GitHub repo secret(`AITCC_API_KEY`)에 넣고 `ait deploy --api-key "$AITCC_API_KEY"`로 소비합니다 — 단 로컬에서는 `--api-key`가 `ps`에 평문 노출되므로 `--profile`을 쓰세요.
:::

## 4단계 — 번들 업로드 (`ait deploy --profile`)

이제 빌드한 `.ait` 번들을 콘솔 배포 큐에 올립니다. `ait deploy`(번들러)는 번들에서 `deploymentId`를 자동 추출해 업로드합니다.

```bash
pnpm exec ait deploy --profile <profile-name> --scheme-only -m "v0.1.2 $(date +%Y-%m-%dT%H:%M:%S)"
```

- `--profile <name>`: 3단계에서 저장한 Deploy Key 프로파일로 인증.
- `--scheme-only`: 업로드 완료 후 마지막 줄에 `intoss-private://...` scheme URL만 출력.
- `-m`: 배포 메모(타임스탬프를 기본값으로).

이 단계까지 끝나면 번들이 콘솔에 올라가 `reviewStatus: CREATED` 상태가 됩니다. 아직 출시 검수에 들어가지 않았고, `serviceStatus`도 여전히 `PREPARE`입니다.

:::info PREPARE 상태에서는 scheme URL을 그냥 열어도 로드되지 않습니다
`serviceStatus`가 `PREPARE`인 동안(출시 검수 통과 전)에는 `intoss-private://` URL을 토스 앱에서 그냥 열어도 번들이 로드되지 않습니다. 검수 전 실기기에서 확인하려면 QR/deep-link relay 주입 경로가 필요합니다 — [번들 디버그 relay](/guides/debug-relay)를 참고하세요. (`/ait debug` 환경 3 경로)
:::

## 5단계 — 출시 검수 제출 (`aitcc app deploy --request-review`)

업로드된 번들을 출시 검수 큐에 제출합니다. `aitcc app deploy`(콘솔 CLI)가 업로드와 검수 요청을 한 명령으로 묶을 수 있고, 검수 요청에는 **릴리즈 노트가 필수**입니다.

```bash
aitcc app deploy <path-to.ait> --request-review --release-notes "<릴리즈 노트>" --json
```

`--request-review`를 쓰면서 `--release-notes`를 빠뜨리면 CLI가 `exit 2`(`missing-release-notes`)로 거부합니다 — 두 플래그는 항상 함께 갑니다.

:::caution 출시 검수 제출은 비가역입니다
`--request-review`는 번들을 `CREATED → REVIEWING`으로 보내 운영팀 검수 큐에 넣습니다. 사용자 측에서 큐를 되돌리는 방법(검수 철회)이 없으므로, 의식적으로 실행하는 동작입니다. 이 때문에 자동 업로드(`ait deploy`)와 검수 제출을 분리해 둡니다 — `/ait deploy` 스킬은 검수 제출을 자동화하지 않습니다.
:::

## 6단계 — 실제 출시 (`aitcc app deploy --release --confirm`)

운영팀이 번들을 `APPROVED`로 통과시키면(보통 며칠 뒤), 같은 번들을 실제로 출시합니다. 이건 검수 제출과 별개의 두 번째 실행입니다.

```bash
aitcc app deploy <path-to.ait> --release --confirm --json
```

`--release`는 번들을 사용자에게 공개하는 비가역 동작이라 `--confirm` 가드가 필요합니다 — `--confirm` 없이 `--release`만 쓰면 CLI가 `exit 2`(`not-confirmed`)로 거부합니다. `--release`는 번들이 이미 `APPROVED` 상태일 때만 성공합니다(`CREATED`/`REVIEWING`이면 서버가 거부). 첫 `RELEASED` 번들이 나오면 `serviceStatus`가 `OPENED`로 전환되어 앱이 사용자에게 열립니다.

## 막힘 해소

### errorCode 4046 — 앱 등록 REVIEW lock

앱이 이미 등록 검수 중(`approvalType: REVIEW`)일 때 `aitcc app register`로 update를 시도하면 `errorCode: 4046`("검수중인 요청이 있어 검수요청을 할 수 없어요.")이 떨어집니다. 이건 앱 등록 검수의 잠금 상태입니다.

```
{ "resultType": "FAIL", "error": { "errorCode": "4046", "reason": "검수중인 요청이 있어 검수요청을 할 수 없어요." } }
```

이때 올바른 대응은 **운영팀이 검수 결과를 낼 때까지 기다리는 것**입니다. 사용자가 직접 검수 큐에서 앱을 빼는 방법은 없습니다(앱 등록에는 검수 철회 엔드포인트가 없음). 잠금을 풀려고 새 앱을 등록하지 마세요 — 새 앱도 같은 잠금에 걸릴 뿐이고, 정리할 잔여 앱만 늘어납니다.

### 약관 미동의 (4037 / 4039 / 4040 / 4099 / 5001 / 5010)

배포·등록이 약관 미동의로 막히면 errorCode가 어느 약관인지 알려줍니다. 워크스페이스 단위 약관은 `aitcc workspace terms`로 처리합니다.

```bash
aitcc workspace terms --json              # 미동의 항목 조회
aitcc workspace terms agree --all --json  # 일괄 동의 (idempotent)
```

`5010`은 워크스페이스 약관이 아니라 **계정 단위 AI 위험 고지 약관(AI_RISK_USE)** 미동의로, 다른 명령을 씁니다 — `aitcc me terms agree --scope AI_RISK_USE --yes`. 동의는 법적 행위이므로 약관 내용을 확인한 뒤에만 진행하세요. `ait deploy`를 직접 실행하기 전에 `aitcc app deploy --dry-run --json`으로 미동의 약관을 미리 잡아낼 수 있습니다.

### 상태 확인 — `app status` vs `app service-status`

앱 상태를 조회하는 두 명령은 권위가 다릅니다.

- `aitcc app status --json` — `/with-draft`에서 client-side로 파생한 상태(`not-submitted`/`under-review`/`rejected`/`approved`/`approved-with-edits`). 빠르지만 derived 라벨입니다.
- `aitcc app service-status --json` — `/review-status` 엔드포인트의 **서버 권위** 상태(`serviceStatus`). 둘이 어긋나면 `service-status`를 믿습니다.

번들 상태는 `aitcc app bundles ls --json`으로 봅니다(각 번들의 `reviewStatus`). 상태에 따라 다음 단계가 갈리는 전체 분기는 `/ait status` 스킬이 안내합니다.

### 런타임 로그는 없습니다

앱인토스 콘솔에는 서버 런타임 로그(stdout/stderr, 예외 스택, 요청별 라인) 엔드포인트가 없습니다. 콘솔이 제공하는 것은 두 가지뿐입니다.

- **커스텀 이벤트 카탈로그** — `aitcc app events ls --json`. 앱에서 `app.logEvent()`로 계측한 이벤트 집계이지 원시 런타임 로그가 아닙니다.
- **전환 지표** — `aitcc app metrics --json`. 노출·전환 등 날짜 범위별 집계. `PREPARE` 상태(미출시)면 빈 배열이 정상입니다.

실 토스 WebView의 런타임 콘솔·네트워크·예외를 관측하려면 on-device CDP relay 경로(`/ait debug` 환경 3·4)를 씁니다. 자세한 운영 조회는 `/ait logs`·`/ait status` 스킬이 안내합니다.
